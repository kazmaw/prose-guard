# approval-summary

spec・plan の冒頭には `## 承認サマリー` セクションを**必須**で置く。

読者は人間レビュアー。**このセクションだけ読めば承認可否を判断できる**情報量にする。詳細を読み直さないと意味が取れない要約は失格。

## 置く位置

- **`brainstorming` の spec**: 本文の前に `## 承認サマリー` を置く。
- **`writing-plans` の plan**: Plan Document Header（agentic workers 注記 + Goal / Architecture / Tech Stack）の直後、最初の Task より前に置く。

## spec の承認サマリーに含める項目

柱は「要件 → 主要な設計判断 → 承認が必要な点」の3つ。この順で置き、残りは補足として後ろに続ける。

1. **要件**: この spec が満たすべきことを箇条書きで。
   - 「何を作るか」ではなく「作った結果どうなっていればよいか」を書く。
   - 背景・経緯・調査結果は本文へ回す。
2. **主要な設計判断**: 別の案を選ぶ余地があった判断だけを、最大5件。
   - 見出しバレットは採用した方針の一言。子バレットは理由を1行1主張で書く。
   - `←` で理由を接続しない（文章リンタが block する）。
   - どのクラス・メソッドで実装するかなどの細目は、本文へ回す。
3. **承認が必要な点**: レビュアーに決めてほしいこと・受け入れてほしいリスク。なければ「なし」と書く。
   - 各項目は「この spec は○○で書いています」と、spec が仮置きした答えを添える。
4. **却下した案**: `| 案 | 却下理由 |` の2列の表にする。
   - メリット／デメリットを文章で書き下さない。
   - 要件を読めば成立しないと分かる案は載せない。却下案がなければ項目ごと省く。
5. **やらないこと**: スコープ外を明示。
6. **影響範囲**: 3行以内で、触る層と互換性・既存データへの影響だけを書く。
   - ファイル一覧は本文へ回す。

**同じ内容を2つの項目に書かない。** 設計判断に書いた「入れない処理」を、やらないことに再掲しない。書き終えたら重複を点検する。

## plan の承認サマリーに含める項目

- **タスク構成**: 全 N タスクを各1行で列挙（何をどの順で作るか）。
- **主要な設計判断**: spec から引き継いだ判断のうち、plan で具体化したものだけ。
- **承認が必要な点**: spec との差分・plan 段階で新たに決めたこと。なければ「なし」と書く。

## ゲートのメッセージに添える一文

User Review Gate / Execution Handoff のメッセージに次を添える。

> まず冒頭の承認サマリーを読んでください。そこだけで承認判断できるように書いています。

## 原則

- 承認サマリーは本体の**代わりではなく入口**。本体の詳細度は従来通り維持し、削らない。
- 書き終えたら各項目について「これがなくてもレビュアーは承認判断できるか」を自問する。できるなら、その項目は中身の薄い穴埋めなので消す（「なし」と書く必須項目を除く）。
- 文章は、prose-guard が注入する文章ルールに従う。

## なぜこうするか

spec・plan の本体は、実装エージェント向けの粒度で長い。
人間が承認判断に必要な情報を拾うには、全文を読む必要があった。
承認に必要な情報を冒頭に集め、人間のレビューのコストを下げます。

柱を「要件 → 主要な設計判断 → 承認が必要な点」の3つに絞るのは、量を抑えるためです。
実装の細目やファイル一覧まで入れると、「ここだけで承認判断できる」量を超えます。

却下した案を表にするのは、メリットとデメリットの散文が長いわりに判断材料を増やさないためです。
`採用案 ← 理由` の形をやめて2段バレットにするのは、文章リンタの `arrow_reason` と揃えるためです。
